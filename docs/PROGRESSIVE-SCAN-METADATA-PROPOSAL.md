# Lux 渐进展示、本地旁车流水线与独立补缺任务方案

日期：2026-09-28

状态：已纳入 `docs/LUX-DEVELOPMENT.md` 阶段 23 / LUX-288 与 ADR-046；运行时代码、数据库 schema 和自动化测试仍待后续任务实施。

## 1. 目标与当前默认假设

媒体项索引提交后即可被前端查询，本地 NFO、海报和其他已存在的图片随即在后台处理；扫描继续发现和提交后续资源。每个条目的本地处理完成后，判断实际仍缺少的元数据和图片，持久化缺失标记，并按策略提交独立的 FILL_MISSING 刮削任务。

草案采用“所有扫描发现并确认缺失的条目自动入队”的范围。全量扫描、实时增量扫描和手动局部扫描共用这一规则，受各入口的自动补缺策略约束。页面正在浏览的条目可以获得处理优先级，但前端打开与否不决定基础任务是否执行。

条目出现与本地处理启动都由“索引已提交”驱动，无需等待浏览器确认已经绘制卡片。两者可能非常接近，本地处理足够快时卡片也可以直接带图出现。

本地旁车处理属于扫描任务的本地阶段；在线补缺属于独立元数据任务。扫描能够产生补缺意向并关联任务，扫描进度与完成状态不等待在线补缺。

## 2. 当前实现与正式规格需要调整的地方

本轮依据当前工作区源码检查；未核验截图对应部署版本、真实媒体路径或浏览器请求，不将以下源码事实作为线上根因证明。

| 当前合同或实现 | 草案要求 | 涉及位置 |
| --- | --- | --- |

## 3. 处理链路

~~~mermaid
flowchart TD
    A[扫描发现有效媒体文件] --> B[有界事务提交媒体索引和本地处理意向]
    B --> C[前端查询到条目]
    B --> D[本地 NFO 和图片后台处理]
    B --> E[继续扫描后续资源]
    D --> F{本地检查是否成功完成}
    F -->|成功| G[登记本地元数据和图片并通知页面]
    F -->|读取失败或根路径异常| H[记录本地错误和重试状态]
    G --> I[按实际数据和策略判定缺失]
    I --> J{是否有可自动补全的缺失能力}
    J -->|有且允许自动补缺| K[提交独立 FILL_MISSING 任务]
    J -->|无或策略禁止| L[保存完整性和阻断原因]
    K --> M[独立刮削 worker]
    M --> N[重新检查缺失并仅补空值]
    N --> O[保存结果和剩余缺失并通知页面]
~~~

例如 A 项已入库、正在读本地海报时，扫描可以提交 B/C/D。A 的本地数据齐全就直接显示；B 在本地检查完成后仍缺海报，就被独立刮削任务领取；此时扫描继续处理 E/F/G。

异步处理允许 B 比 A 更早完成。前端列表仍遵循分页和排序，首页只显示既有有界栏位，不将全部资源强行塞入首页。

## 4. 索引可见性与删除安全

1. 页面只能读取已经提交的媒体索引。事务回滚的资源不发布可见通知。
2. 首批结果尽早提交，随后恢复正常有界批次。采用首批较小的刷新边界及时间预算作为候选，避免 1000 项恰好落入一个大批次时完全没有渐进展示。
3. 具体批次数量与时间预算由同 fixture 性能结果确定。候选首批通知预算为 250ms，常规通知合并窗口为 500ms 至 1s；这些值是调优起点，不是已达到的时延承诺。
4. 扫描中逐批刷新包含已提交的新增/变更和仍保留的旧资源。未观察到某个旧资源，不代表可以将它隐藏或删除。
5. 完整根路径覆盖、设备/inode 校验、删除前二次文件确认和基线 CAS 继续控制 REMOVE。不可用/不完整根路径、取消与 I/O 错误不会造成批量删除。
6. 计数区分“当前可浏览项数”和“本次已发现项数”；扫描期间不宣称最终总量已确定。
7. 保留 ScanCompleted 表示索引及安全缺失确认完成的既有语义；本地队列未结束时扫描可处于 POSTPROCESSING，全部本地阶段结束后回到 IDLE。在线队列独立展示。

## 5. 早期本地工作入口

推荐为新流程增加持久化、有界的本地批次 outbox，而不是让本地 worker 直接等待现有末尾 target 物化。建议表名为 scan_local_metadata_batches；精确 migration 编号在实施时按当时仓库分配。

- 正向媒体索引与对应本地处理意向在同一个短事务提交，提交成功后再唤醒 worker。进程内 Notify 只负责唤醒，不作为唯一任务记录。
- 批次保存 scan_job_id、library_id、根路径身份、批次序号和有上限的目标引用；引用携带稳定 source/item 标识、相对路径和输入版本。候选上限为每个意向 256 个 source 引用，一个索引提交批次可以产生多个意向；最终以序列化大小和数据库基准确认。只保存执行所需定位信息，不保存完整媒体目录内容。
- 使用批次行、领取游标和有界未完成记录，避免重新把全量扫描的重型逐文件后处理目标搬回正向提交主路径。必须测量额外写入量、事务耗时和 WAL。
- 领取与完成幂等；同一媒体项多个 source、同一目录的剧集父节点，以及全量/增量交叠，通过当前有效输入版本合并处理。
- 新增/变化项、未完成本地检查项、旁车发生变化项进入本地检查。媒体文件未变不代表旁车未变；完整无变化重扫需要复用可验证的旁车版本，不能漏掉新添加的 NFO/海报。
- 最终 scan_job_targets 物化时，复用已经完成的本地处理结果，初始化对应 METADATA 阶段状态，避免末尾再读一遍 NFO 和图片。
- 现有 target-ready 屏障继续保护其余依赖最终 target 集的工作；新增本地入口明确采用自己的根身份和输入版本保护。
- 用流程版本控制启用范围。旧任务执行器沿用旧路径，不能让旧队列和新 outbox 对同一条目各处理一次。

内存队列满时保留数据库中的未领取工作，扫描继续提交可恢复意向。worker 每次只加载一个有界窗口，不把整库目标拉入内存。

## 6. 本地旁车处理与图片优先

扫描负责发现和索引；本地 worker 负责本地目录中的 NFO、图片、内容标签及相关索引。读取文件与图片解析位于后台，不在列表或详情 GET 请求中执行。

本地 NFO 与图片识别应允许独立推进：海报已确定时即可登记并通知页面，无需因同条目的 NFO 读取较慢而延迟出图。完整缺失判定仍等待该条目的相关本地检查全部进入确定状态。

本地阶段使用共享的、有界目录缓存，并建立按规范化文件名查找的目录索引：

- 同一目录复用目录项枚举；不同影片根据现有 basename、图片类型与命名优先级查找候选。
- 相同目录/输入版本的缓存跨本地 worker 批次复用，不能每处理 16 项就重建整份目录索引；容量达到上限时按目录淘汰，并尽量合并同目录工作。
- 保留现有文件名和扩展名优先级，避免优化后选中另一张图片。
- 图片登记只处理实际候选，已验证未改变的图片复用其已有登记结果；内容版本变化时更新图片标签。
- 缓存按目录/输入版本失效并限制条目数或内存量。新增、删除、重命名旁车和文件系统监听事件都参与失效。
- 目录读取只完成第一页时，尚未出现海报不能判定为缺失。缺失必须建立在完整候选范围检查上。
- 全局图片读取继续有硬上限。跨媒体项的本地并发先以 2 至 4 路作为调优候选，同时限制数据库落库并发，按 SQLite/PostgreSQL 与前台延迟结果确定配置。

系列、季度与分集复用同一机制；父节点去重处理，继承图片按现有展示策略判断是否可用。多个媒体源任一有效来源已提供所需数据时，不因另一个来源缺图片而重复刮削。

## 7. 本地状态、缺失标记与任务状态

三个维度分别记录，避免把“任务结束”当成“数据齐全”：

| 维度 | 建议状态或内容 | 用途 |
| --- | --- | --- |
| 本地处理 | PENDING、RUNNING、READY、FAILED、CANCELLED | 表达是否完成检查；READY 可以是没有任何旁车 |
| 实际缺失 | 缺失能力/字段/图片类型、checked_revision、checked_at | 显示“缺海报”“缺简介”等，并驱动后续策略 |
| 在线任务 | 未提交、QUEUED、RUNNING、WAIT_RETRY、待确认、无可用结果、完成、取消 | 复用现有刮削作业/能力尝试状态，反映补缺执行情况 |

建议以 item_metadata_completeness 保存本地确认版本、实际缺失与阻断原因；执行状态优先关联现有任务数据，不再复制一套刮削队列。

关键规则：

1. PENDING/RUNNING 表示尚未确定，不能因为暂时没有图片标签就发起在线补缺。
2. 本地目录检查成功且没有相应文件，才能确认真实缺失。多 source 或父级图片继承还存在待检查范围时，不提前宣告缺失。
3. 权限错误、损坏文件、根路径离线、根身份改变属于本地处理异常，先记录并重试，默认不将其转为在线刮削需求。
4. 已有 Lux 管理的图片、其他有效媒体源或策略允许的继承/回退图片应纳入可用性判断，不能只检查影片同目录有没有 JPG。
5. 图片类型关闭、不适用字段、结构性统计和锁定策略不会产生无法自动执行的请求；锁定的空字段可以记录缺失及 LOCKED 阻断原因。
6. 文件名回退标题只表示可展示，不把它自动当成已经确认媒体身份的证据。
7. 真实缺失和“当前需要向 provider 请求的能力”分开保存。provider 明确无结果时仍可能缺图，但已有无结果记录会阻止无限重试。
8. 一次刮削只补好了海报，就清除海报缺失；简介仍缺则继续保留其标记。

缺失计算复用 MetadataRequestPlan 与当前图像/字段策略，补充提供“实际缺失”视图，不能复制一套与手动 FILL_MISSING 不一致的判断逻辑。

## 8. 独立在线补缺调度

本地阶段成功完成后：

1. 根据当前数据、锁定字段和策略计算实际缺失，持久化完整性结果。
2. 从实际缺失计算可执行的 FILL_MISSING 请求计划，结合 provider 能力、已有 UNAVAILABLE 记录、冷却时间及自动补缺开关。
3. 在保存缺失标记的同一事务记录调度意向。独立 dispatcher 将意向合并到现有 metadata_reidentify_jobs，防止“标记写好了但进程在入队前退出”的遗漏。
4. 按小批次合并缺失项，复用现有单次最多 100 项的定向作业入口；持续扫描可提交后续批次，不创建一项一个整库任务。
5. 对同一 item 和有效数据版本检查已排队/运行的自动及手动作业。已有活跃任务时合并需求或让它完成后重新判定，避免重复 provider 请求。
6. worker 真正执行时重新计算缺失；排队期间本地海报已经补齐，则跳过对应请求。已确认 provider ID 可直接用于图片补缺。
7. 只补缺，不覆盖本地数据、已填字段和锁定值。身份不足时沿用现有自动匹配置信度与待确认流程。
8. 保存在线结果后重新计算实际缺失，发布页面更新；成功但无数据、无候选、provider 不可用分别记录原因和重试条件。

在线并发复用现有进程全局额度：当前 SQLite 默认 4、PostgreSQL 默认 8、硬上限 16。扫描、本地读盘、在线网络分别受控；前台压力升高时降低后台并发。

可见条目优先级属于可选增强。首版先保证新提交批次及时开始处理和公平排队；若需要前端主动提升优先级，使用有鉴权、去重与数量上限的显式意向接口，GET 页面请求本身保持只读。

## 9. 入口策略与兼容

| 入口或情形 | 本地检查 | 独立在线补缺 |
| --- | --- | --- |
| 全量扫描 | 索引提交后逐批开始 | 草案目标开启，确认缺失且允许自动补缺才提交 |
| 实时增量扫描 | 只处理本次受影响内容 | 尊重现有 realtime_metadata_auto_match_enabled，确认缺失后提交 |
| 手动扫描所在文件夹 | 只处理对应范围 | 通过局部扫描补缺策略控制，不扩大到整库 |
| 没有配置或没有启用刮削器 | 正常进行 | 保存缺失和阻断原因，不进行网络请求 |
| 自动补缺关闭 | 正常进行 | 保存缺失，管理员可手动 FILL_MISSING |
| HOMEVIDEOS / VIDEO / FOLDER | 支持对应的本地规则 | 沿用禁止在线自动识别的类型边界 |
| 本地读取失败、根路径不可用 | 记录错误与重试 | 本地结果未确定，暂不提交 |

推荐增加“全量/手动扫描发现缺失后自动补缺”的独立策略，与实时增量开关区分。已有明确关闭的实时开关继续生效。升级不在 migration 中访问网络或对历史全库自动补缺；现有库是否启用新策略需要明确记录配置来源，不能用开启新能力来覆盖旧的关闭意图。

## 10. 页面更新与图片展示

- 首次索引提交、本地图片登记、元数据补齐各自产生可合并的更新意向。复用现有用户 SSE 的 invalidate/home 通路，按时间窗口合并发布。
- 只在提交成功后通知。客户端失去连接并重连时主动重取当前活跃页面，以数据库状态兜底。
- 首版刷新当前已加载的首页、媒体库分页及相关详情查询；离线或不活跃查询只标记失效，避免全库刷新。
- 原地更新图片/文本，保留滚动位置与当前选择；首次扫描可以追加符合当前排序的项目，不强制逐文件滚动。
- localMetadataPending 继续兼容，并覆盖全量与增量的新本地队列。需要展示缺失原因与补缺进度时，再增加可选 DTO 字段及对应类型。
- 页面可区分“读取本地数据”“等待补全”“正在补全”“需要确认”“缺失且无法补全”；任务失败或取消后等待动画必须停止。
- 海报标签更新后使用新图片 URL，防止仍显示旧缓存；可见区域图片及时请求，屏幕外图片沿用懒加载。
- 页面通知合并与后台首页刷新都应限频，不能每处理一张图片就为所有用户重建首页。

## 11. 并发、取消、恢复与身份保护

每次本地和在线结果写入前校验当前根身份、source 有效性及相关输入版本，不能让较旧任务覆盖较新本地编辑或新的实时扫描结果。版本变化时放弃旧结果，重新安排当前版本。

FILL_MISSING 应用仍在落库阶段复核空值和锁定状态，避免请求期间新添加的本地 NFO/海报被覆盖。身份合并遵循现有合并事务，目标发生合并时解析当前 canonical item，再迁移或去重任务引用。

取消扫描停止新的扫描发现与对应未完成本地工作；已提交媒体继续可浏览。已提交的独立刮削任务有自己的取消入口，取消扫描不会隐式撤销它们。删除媒体库则阻止两类任务再写入该库。

服务重启沿用既有取消/恢复合同。未完成本地工作保留明确终态或可重试记录，不能遗留永久 PENDING；管理员重试只处理未完成或输入已变化项。在线任务沿用现有任务恢复、重试和尝试历史。

本地失败不阻塞后续资源索引；在线失败不把扫描记为失败。任务详情分别记录索引数量、本地已完成/失败数量以及关联补缺任务，不能把后者计入扫描完成百分比。

## 13. 验收场景与指标

| 场景 | 必须观察到的结果 |
| --- | --- |
| 1000 项全部具备所需本地元数据/海报 | 第一批先于扫描末尾可查询；本地图片持续登记；独立在线请求数为 0 |
| 1000 项中部分缺图片或字段 | 只有本地检查完成且策略允许的缺失项进入补缺；已有内容保留 |
| 首项图片读取人为阻塞 | 索引能提交后续条目；其他本地项可推进；首项未被误判缺失 |
| 海报存在、NFO 读取较慢 | 本地海报先显示，完整性判定等待 NFO 检查结果 |
| 同一目录平铺大量影片 | 目录枚举有界复用；名字匹配次数不随“影片数 × 目录项数”增长 |
| 目录分页后段才出现海报 | 不在第一页后错误触发在线补缺 |
| 本地权限错误或离线根路径 | 显示读取异常/待重试；无错误删除和误触发补缺 |
| 排队后用户新增本地海报 | 在线 worker 重新检查并跳过该图片请求 |
| provider 无候选/不支持/超时 | 保存原因和剩余缺失；遵守有限重试与冷却，不无限建任务 |
| 全量与实时扫描命中同项 | 最新输入优先、活跃工作去重，旧结果不覆盖新数据 |
| 扫描取消或服务中断 | 已提交资源可浏览；本地状态有明确终态/重试；独立任务合同清楚 |
| 未配置 provider、自动补缺关闭或 HOMEVIDEOS | 本地正常展示，在线请求数为 0 |

记录首批索引提交、首批前端可见、首张本地海报标签可用、首张海报请求完成、全量索引完成、全部本地处理完成及在线补缺完成的独立时间点。证明渐进处理至少需要“第一批本地处理开始 < 全量索引完成”的运行时证据。

性能用同目录布局、同 fixture、同构建配置的 SQLite/PostgreSQL A/B 比较；同时观察索引总耗时、事务次数、DML/WAL、目录枚举、前台 p95、内存与队列积压。候选若让索引或前台 p95 稳定回退超过项目既有 5% 观察门，应调低并发/通知或修改批次实现，不以海报提速掩盖扫描退化。

测试时先确认 /Volumes/Toshiba 已挂载，Cargo 命令统一设置 CARGO_TARGET_DIR=/Volumes/Toshiba/mywork/Lux/target。本机 ARM 结果只证明本机行为和性能，NAS/x86 需要目标环境实测。
